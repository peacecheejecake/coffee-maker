# 0001. 이벤트 소싱 장부와 Decider 패턴

- 상태: 채택 (2026-10-23)
- 관련: DESIGN.md §5.1, §5.3 / PLAN.md M0

## 맥락

정정 이력, 되돌리기, 탕감 투표, 멀티 디바이스 동기화, 연출 트리거가 모두 "무엇이 언제 바뀌었나"를 필요로 한다.
상태를 직접 수정하면 이 다섯 가지를 따로 구현해야 하고, 기기 간 충돌 해결이 어렵다.

## 결정

1. 모든 변경은 append-only `LedgerEvent`로 기록하고, 상태는 `project(events)`로 계산한다.
2. 커맨드 처리는 `decide(state, command, ctx) → Result<events, DomainError>`, 상태 전이는 `evolve(state, event) → state`로 분리한다.
   - `decide`는 사용자에게 보여줄 **검증과 에러**를 담당한다.
   - `evolve`는 **절대 실패하지 않고**, 현재 상태에 맞지 않는 이벤트(기한 지난 투표, 중복 발의, 닫힌 기록 정정 등)는 무시한다.
     동기화 경합으로 같은 커맨드가 두 기기에서 동시에 승인돼도, 같은 순서로 재생하면 모든 기기가 같은 상태에 수렴한다.
3. 계산 결과(지각 분, 잔 수)는 이벤트에 **저장**한다. 규정이 바뀌어도 과거 기록이 재해석되지 않는다.
4. 시간 창 규칙(철회 10분, 투표 기한)은 `serverAt ?? at`으로 판정한다. 동기화 후에는 서버 시각이 기준이 된다.
5. 투표 결론(가결/부결)은 별도 이벤트 없이 투표 이벤트에서 결정론적으로 도출한다. 기한 만료만은 시각이 필요하므로 selector(`proposalStatus(p, now)`)에서 판정한다.
6. 한 기록의 표시 컵 수는 항상 `max(0, 청구 잔 수 − 상환된 잔 수)`. 이미 낸 커피는 되돌리지 않고, 청구가 줄면 차액은 `overpaid` 통계로 남는다.

## 결과

- (+) 수정 이력·undo·감사 추적이 공짜로 생긴다. 동기화는 이벤트 union + 서버 seq 정렬로 단순해진다.
- (+) `core`가 순수 함수뿐이라 속성 기반 테스트로 임의 이벤트 순서에 대한 불변식을 검증할 수 있다.
- (−) 이벤트 스키마 변경 시 upcaster가 필요하다 (`upcast.ts`).
- (−) 이벤트가 수만 건을 넘으면 전체 재투영 비용이 생긴다 → 필요해지면 확정 seq 지점의 스냅샷 캐시로 해결 (M3).
